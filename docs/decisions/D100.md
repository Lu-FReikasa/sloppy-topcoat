# D100 — A new chat reads the key terms of the latest chats; there is no hand-over note

**Decision.** **The hand-over note between chats (the *episode*, E3-06) is gone. What a new chat knows of the latest chats comes from their running summaries (`chat_digests`, D75/E5-01), shown as key terms.** The running summary is updated after every answer (pass 1) and checked by a second model when the chat rests (pass 2). Its verified statements are written as `key term: short explanation` (at most 120 characters), and the core block's section "Discussed last" lists, for the latest one or two chats **of the same program** from the last 14 days, as many of these statements as fit the section's budget (150 tokens, newest statements first, shown in the order they were made). The chat that asks is left out, and so are digests without a verified statement.

**Why.** Two things wrote one record. The after-answer writer and the 5-minute tick made a hand-over note from the chat, and the checked summary of the digest overwrote it. The note was a second summary of the same thing, with its own model calls (the most frequent job of the hub: 252 of 295 jobs on 2026-11-03), its own settings (six), its own task in the background flows, its own kind in the memory and its own page. It also failed silently: a model that thinks used up the 300 tokens for its thoughts, the note came back empty, nothing was stored, and the tick tried the same conversations again every five minutes. A running summary needs no extra call, is already checked, and every statement in it rests on a quote of the chat (D75). Key terms with a short explanation take less room in the prompt than running text and are easier for a model to use as a starting point than a paragraph.

**How it is built.**
- `DigestStore.recent(...)` reads the latest digests of one program (`conversations.application`, default `chat`), `core_rules.RecentChat` carries them, `core_rules._recent` renders them. Each chat takes its share of the budget, so the newest cannot starve the one before. The stamp of a conversation's core block includes the chats and their last message, so a changed summary changes the block of a *new* conversation only (a running one keeps its block byte-identical, D38).
- The summary prompt (`chat_digest.SUMMARY_SYSTEM`) asks for `key term: explanation`; a statement without a colon is still shown as written.
- Removed: `core_episodes.py` (writer, tick, wait for the note), the `episode` kind and its half-life/expiry rules, `core_episode_*` settings, the background task `episodes`, `store.episodes/episode_of/renew_episodes`, the memory page's list of runs, and the `episodes` part of `GET /api/core` (now `recent`, `core_recent_*` settings). Migration `d100_drop_handover_notes` deletes the old rows (`kind = 'episode'`) and their runs.
- The job label `episode` stays in the web's list of work kinds so that old job records still read.

**Consequences.**
- A chat that was never summarised (nothing verified, no memory, incognito) is not "discussed last". A chat from another program is not either: a program's memory is its own (D74).
- The key terms are as good as the summarising model. A statement that quotes the chat wrongly is not verified and does not appear.
- Not decided here: whether a longer history (older chats, by topic) should be offered on demand to the assistant instead of by a block; the recall of notes is the place for that.
