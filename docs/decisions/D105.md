# D105 — Applications as plug-ins: data in the hub, code only as a node of its own

> **Status (2026-11-26):** Confirmed (the maintainer, 2026-11-25): built as planned, in this order. Step 1: the manifest (`proto/plugin/manifest.schema.json`) and the built-in programs described by it. Step 2: the registry (`hub/src/topcoat_hub/plugin_registry.py`, tables `plugins`, `plugin_versions`, `plugin_changes`; admin API `/api/plugins`, GUI: Administration › Applications › Plug-ins). The built-in programs are registered as version 1.0.0 and can be updated and rolled back, not switched off or removed. A manifest's `agent.tools_ceiling` narrows its program's ceiling (applied in `app_scope.ceiling`), never past the contract; a plug-in that is no program has no tools. Every change is audited and published as `ui_plugins`. Next: the Clipper plug-in (#20) and the GitHub tool plug-in (#21). Views stay fixed types; Theme v2 (D113) builds on this registry and these types.

**Decision.** An application (Chat, Research, Development, Administration, Projects, Settings, and every later one) is
described by a **manifest** (`proto/plugin/manifest.schema.json`): its instructions (AGENT.md), its tool ceiling, its kinds of
steps (Phase 1), its block programs, its views, its **commands** and **menus**, its settings and its texts in English and German.
The hub is the small core: routing, rights, the gateway, the queue, the database, the checks and the plug-in registry.

There are three kinds of parts, and they are updated differently:

| part | what | update while the hub runs |
|---|---|---|
| **data plug-in** | manifest, AGENT.md, block programs, kinds of steps, commands and menus, views (fixed types), texts, theme, persona | yes, at once: the hub reloads it from the database; every version is kept, one click goes back |
| **tool plug-in** | its own process that connects to the hub **like a node** (pairing, signature, whitelisted, schema-checked capabilities) | yes: the process is replaced; the hub sees the "node" leave and come back with a new version |
| **core** | the hub itself | a restart of the container (seconds); clients connect again |

**Views are fixed types** (`chat`, `list`, `table`, `form`, `report`, `board`, `tree`) with a data source. A plug-in brings no
code into the GUI and none into the hub process. A new kind of view comes with a release of the client, not with a plug-in.

**Commands are one list.** `GET /api/ui/commands` lists what a person may do (open a program, a view, an action), with a text key,
the program, a shortcut and the right it needs. The command palette, the menus a theme draws, the tray and the selector of the
desktop client, and the Windows command palette (PowerToys) all read this one list.

**Why.** An application is about 80 % data already (prompt frame, tool ceiling, views, settings, block programs). Updating that
part while the hub runs is cheap and safe. Foreign code inside the hub process would break the security baseline; the node
protocol already gives what a tool plug-in needs (outbound connection, whitelisted actions, schemas), so a tool plug-in is a node.

**What does not change.** The baseline of `CLAUDE.md`: nodes execute only named, schema-checked actions from a whitelist; a
plug-in can narrow rights, never widen them; the assistant proposes and a person confirms (D15, D83).

**Order.** (1) Manifest schema and the built-in programs described by it (no change of behaviour), `GET /api/ui/commands`.
(2) Registry table with versions and rollback, install/update/remove of data plug-ins (admin), live reload over the event stream.
(3) Clipper as the first plug-in that is not built in. (4) The GitHub tool as the first tool plug-in.

**Decided with the maintainer on 2026-11-11** (plan `2026-11-11-desktop-plugins-clipper-kontext-plan.md`, E3/E4).
