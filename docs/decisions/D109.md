# D109 — A large task is a task node in Projects; its sub-tasks form a DAG the hub coordinates

> **Status (2026-11-25):** Decided by the maintainer (plan of 2026-11-24, E3 and open decision 1; place of the large task confirmed 2026-11-25). Not built: milestone P2 *Large tasks as projects*. Not to be confused with the read-only coordinator of [D44](D44.md).

**Decision.** **A task too large for one issue fix becomes a *large task*: a task node in one of the person's projects. A model proposes its sub-tasks once, in a fixed schema; the hub checks them, files them as child nodes of that task linked by `blocked_by`, and coordinates them in code. Decomposing is free inside the project's grant.**

- **Where it lives.** The large task is an ordinary `task` node of an existing project (made by the person, the project agent, or later the secretary of [D112](D112.md)). Each sub-task is a child `task` node of it; a dependency is a `blocked_by` relation between two sub-tasks. The project's tree, relations, loop check and Akte are used as they are; there is no new store for large tasks.
- **Who plans.** The block program `decompose` (code model of the house, [D117](D117.md)) gets the task text, the repository map and the Development contract ([D118](D118.md)) and answers in the schema `proto/agents/outputs/decompose.schema.json` ([D119](D119.md)). A model is asked at only three points: *decompose*, *replan one branch* of the DAG, and *summarise* at the end. No model steers the run.
- **A sub-task** has: `id`, `title`, `goal` (one sentence), `layer` (one of store, api, gui, proto, docs, admin, research), `files` it changes (at most three, existing), `symbols` it touches, `new_files` (only under allowed paths), `accept` (each criterion machine-checkable: a test name, an endpoint, a screenshot, or prefixed `person:`), and `depends_on` (ids of other sub-tasks).
- **The hub checks, not a model.** Files and symbols exist in the repository map; new files only in allowed places; at most three files and one layer per code sub-task; at most 8 sub-tasks per large task; every `depends_on` names a sub-task of the same answer; no cycle. A refused decomposition gets back the list of *all* problems at once, and the model may answer again.
- **Free inside the grant.** A new grant target `project: {decompose}` (`project_scope.TARGETS`, level `free` or `confirm`, as every grant) lets the project agent create and change sub-tasks under a large task without a change set and a click. It never deletes a node: a dropped sub-task is closed, not removed (`delete` stays in `project_scope.NEVER`). Without the grant, a decomposition is a change set the person confirms as today.
- **Running.** The coordinator (`vorhaben.py`, issue #32) starts each sub-task whose dependencies are done through the existing issue pipeline (investigate → steps → workshop). Reading and planning sub-tasks may run in parallel; **writing runs one at a time** on the branch `topcoat/v-<nr>` of the large task, because the workshop keeps one copy per repository. The hub accepts a sub-task when its tests are green, its screenshot exists where one was asked for, and the changed files equal the announced ones.
- **States** of a sub-task, as the view of issue #33 shows them: `waiting` (dependencies not done), `running`, `failed`, `blocked` (needs the person), `done`. A large task is done when every sub-task is done.
- **Failure.** The same failure fingerprint twice ([D120](D120.md)) blocks the sub-task; the hub asks `decompose` once to *replan that branch only* (the failed sub-task and those that depend on it); if that fails too, the sub-task goes to the person as an inbox item. Other branches go on.
- **The end.** When all sub-tasks are done, the person gets **one roll-out click** for the whole large task (the collected diff of `topcoat/v-<nr>`, through the spool of [D104](D104.md)).

**Why.** Features such as "model, migration, store, API and GUI" need more than the six steps one issue fix allows, and one pipeline unit per issue cannot grow with the task. A coordinating *model* would hold the one code slot all the time and add a source of error; in the research behind the plan only the strongest models delegated reliably. The hub already keeps books (project tree, relations with loop check, batches, iterations, the repeat rules of D83), so it coordinates in code and asks a model only where judgement is needed. A task node rather than a project of its own keeps a large task next to the work it belongs to and reuses the project's grant, Akte and views (maintainer, 2026-11-25). Decomposing only creates and changes plan items in Projekte, nothing outside it, so a click per item is friction without protection.

**Not decided here.** Writing in the workshop without a click per fix is [D110](D110.md). Large tasks that span several repositories, and sub-tasks in `desktop/` or `node/` (they stay with Claude Code).
