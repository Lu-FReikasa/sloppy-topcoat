# D113 — Theme v2: a theme arranges registered views with an engine

> **Status (2026-11-25):** Decided by the maintainer (plan of 2026-11-24, recommendation 6; shaped by the confirmation of [D105](D105.md) on 2026-11-25). Not built: milestone *P5 Themes v2*.

**Decision.** A theme stays **data plus CSS, never code** ([docs/THEMES.md](../THEMES.md), plan E4). Version 2 adds three things to the fields of today (base, layout, bar, chrome, motion, css):

- **An engine:** `desktop` (today's windows, taskbar and layout kinds, including `nest` from the Trellis-inspired work), `single` (one program at a time, like a classic web app) or `dashboard` (a grid of views, like a home dashboard). Engines are trusted code in the web build.
- **Regions and placed views:** a theme names regions (CSS grid areas) and which views stand in them per program. A view is a view of a registered plug-in ([D105](D105.md)): a fixed type (`chat`, `list`, `table`, `form`, `report`, `board`, `tree`, `module`) with a data source. An unknown view id is refused when the theme is saved.
- **Assets:** images and sprite sheets by reference to hub files ([D114](D114.md)) instead of inline `data:` URIs.

Every engine must work in the **overlay** of the desktop client and in **solo** windows; that is part of accepting an engine. A trusted shell (sign-in, approval cards, confirmations, error boundary) stays outside the theme's reach: theme CSS is nested under the desktop root and cannot style it. The settings get a **gallery** with preview images per theme version.

**Why.** The maintainer wants themes that decide *what is shown how and in which windows*, from wholly different ideas, all on the same backend interface; the desktop stays as one theme. Building on the registry keeps one list of what exists, and fixed view types keep code out of themes and plug-ins.
