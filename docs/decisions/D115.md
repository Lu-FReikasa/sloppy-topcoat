# D115 — Pools per node, functions per program, block programs instead of flows

> **Status (2026-11-25):** Restored. Decided on 2026-11-04 as D104 and built in rounds R1 to R7 (pools 2026-11-05, flows removed 2026-11-06, block programs in `hub/src/topcoat_hub/blocks/`, [docs/BLOCKS.md](../BLOCKS.md)); the number D104 was reused on 2026-11-17 for the fix roll-out, so this text was lost from the folder. Amended by [D117](D117.md): with house models the model lists of the rows no longer decide.

**Decision.** **What may run where is set in three places only, and each answers one question.**

1. **The pool of a node** answers *which models may be used on this machine*: the admin marks one or more of the models that lie on a node as **available**. A model that is not available on a node is invisible to every program and to the queue on that node. Nothing else decides this.
2. **The program** (Chat, Research, Development, Administration, Projects, and the independent program **Background**) answers *who may use what*: its prompt frame, its tool ceiling (D69, applied by one door: D116), which part of the pool it may draw from (nodes, models, priority, waiting time) and its **functions**.
3. **A function** of a program answers *what happens and with which model*: it is a **block program** — a trigger (hat) with a stack of fixed, typed blocks. Every block that asks a model carries a **pick**: a rule that chooses model and node from the program's pool ("fastest node first, whatever is loaded", "best rated for this kind of work, may displace idle models", "another model than the author's").

**The flows (the n8n-like graph editor, its engine and its page) are removed.** On the production hub there are 12 flows and one flow run in total (a test from 2026-10-22). Flows served as a container for settings (the chat policy per effort level, the background tasks), not as a means to run work. Their run and event plumbing (live view, numbered events, replay) is kept for block programs.

**Block programs are trees, not free graphs.** Scratch is the model: a stack of blocks; some blocks are C-shaped and hold stacks of their own: *if/else*, *repeat until* (always bounded: a setting and a progress guard, never endless), *parallel* with lanes and a *merge* (consensus, majority, best by rating, or a model that sums up), *for each*. Values live in named variables and are typed (text, report, verdict, evidence, pick, list), so a block only snaps where its input fits. A program always terminates, can be validated before it runs, shown as a picture, and run dry against fake ports in tests. The agent run keeps its loop in code (it streams and is time-critical); what the admin edits are its **hooks** — slots before and after each tool call, on a repeated call and before the run finishes — into which check blocks go (step check, evidence check, repeat guard, second reader).

**Models are classified.** Every model has kinds (chat, embedding, vision, speech) and capabilities (tools, thinking, long context), each with its source: *detected* (name, later the GGUF header), *proven* (a probe the hub ran: it answered a tool call, it embedded) or *set by the admin*. Programs filter by them. A hard "at least 27B" filter is not part of the design: the **benchmark** finds suitable models. Deterministic suites per kind of function (no model as judge) give a rating and a speed per model; a pick can say "best rated" and may state a speed floor. The benchmark may also tune the inference parameters of a model for a function (temperature, thinking effort, context); the result is the **profile of the model for that function** and is applied by the pick. A suggestion changes a program only by the admin's click.

**Why.** (a) Model choice is decided in eight places today (the table, the pick in the chat, `quality_models`, parameters of flow nodes, background flows, the hub default, the stage limits, the hand-over); D85 wanted one. (b) A pool per machine reflects how the hardware is used: the PC of the maintainer is also a node and only a few of its models should ever be picked. (c) What a program does after an answer or a report (check, revise, second reader, consensus of two nodes) is the interesting configuration, and a fixed list of settings cannot express it. (d) Measured on 2026-11-04: a dense 27B at Q2 gives 1.5 tokens per second on an 8 GB card; size alone is a bad filter, a rating with a speed floor is not.

**What does not change.** The security baseline of `CLAUDE.md` holds: a block can only remove rights, never add them (the ceiling of D69 and D116, the rights of the person and the node whitelist stand outside the blocks); nodes execute only whitelisted, schema-validated actions; the assistant proposes and a person confirms (D15, D83); no call to an external LLM API without the redaction layer. User rights (who may see a program) stay in the user administration.

**Consequences.** The pages *Models*, *Flows* and *Programs & rights* become one configuration area: **Programs** (a list; one program opens with prompt, tools, pool and priorities, and its functions with a block editor, a live view and a preview of who would be chosen now) and **Models** (the inventory per node with the pool switch, tags and ratings). `quality_models`, the parameter `model` of the second-look node, `handoff_*`, the hub-wide default model and the flow tables go; the plan and the order were the brief PRG-00 (outside the repository since 2026-11-25). This replaces the open parts of D85 (one table) and of the flow engine (E7-05), and takes over SCH-05/SCH-06/QLT-01 where they overlap.

**Decided with the maintainer on 2026-11-04.** The chat has **no model choice for anyone**; the model comes from the pick of the function (API clients of `/v1` still name a model, which must be in the pool). The old chat view goes; the Chat program gets an **Admin** entry at the end of its rail with a tool picker that reaches everything the person's grants allow. "Fine-tuning" is the setting of the best inference parameters for the hardware, not training. **Consensus is a third agent that compares the results** (anonymised, order shuffled, a model other than the authors where the pool has one); candidates may run one after the other (brief PRG-00, 3a). Tests stay off node-amd until the results are good. The flows are exported and deleted.

**Not decided here.** Whether the nodes report GGUF facts (needs a node release; proposal: later, optional, own permission).
