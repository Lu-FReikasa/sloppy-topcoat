# D116 — One application profile: run, prompt and rights of a program in one place

> **Status (2026-11-25):** Restored. Decided and built in a first slice on 2026-11-04 as D103; the number D103 was reused on 2026-11-17 for the issue fix, so this text was lost from the folder. Slice 4 is settled by [D115](D115.md) and [D117](D117.md) (no hub-wide default model setting); the contracts ([D118](D118.md)) now state each application's role, tools and limits.

**Decision.** **What a program is allowed (its tools), how it works (its run: limits, effort, frames) and what it says (its prompt frame) are read from one profile per application, and every task of a program starts through one door that applies it.** The profile is not a new store: it is the template of the program (`ui_templates`, `agent` block: tool ceiling and frame) plus its row in the table of applications (D85: models, nodes, priority, waiting time) plus the named run sets of `research_profile` (D101). What is new is the rule that nothing around it decides for itself.

**Why.** Rights, run and prompt of a program were assembled in four places that each remembered a different part: the chat check (scope and limits), the project request to a program (prompt only), the Ablage (revision: prompt only) and the task API (nothing). The ceiling of a program (`app_scope`, PLATFORM 3.1) was applied where a conversation's scope is settled, so a task that started any other way ran with every tool of every machine. Seen live on 2026-11-04: a Research revision carried 49 tool definitions (42,000 characters) into a model with a 16k context and ended with "context full" before it had read a page. A request from a project to Research or Development had the same hole. Settings with the same purpose existed twice (`quality_models`, `second_look_model`, `handoff_slow_nodes` next to the table).

**Built (first slice, 2026-11-04).**
- `AgentService.start` narrows the scope of every task that names a program (`chat`, `research`, `dev`, `admin`, `project`) to that program's ceiling (`_within_application`, `app_scope.cap`). The ceiling only removes; a narrower scope stays. A caller can no longer forget it. The two Research starts that applied it by hand (`POST /api/agent/tasks`, revise in the Ablage) now rely on this door.
- `POST /api/agent/tasks` takes `application: "research"` and `depth`; the task view shows its `scope`.
- The report tools (`messages` node) belong to no tool group and survive every group choice (`tool_groups.apply_scope`).
- `stop_reasons.py`: one table for why a run ended (a neighbour, not part of the profile).

**Consequence found by the first slice.** A Research run can no longer look at a machine (Docker logs of a server): its ceiling is the web and the notes. That is the design (PLATFORM 3.1: what lies outside is asked of the application that has it, by a hand-over). Tests that used Research for machine evidence lift the ceiling with the fixture `open_ceiling`.

**Next slices, each with the decision it needs first.**
1. *Run sets in the profile.* `Limits` has 25 fields that mix the server check and Research. Name the sets (`check`, `research.quick|default|thorough`, `dev`) and let the program pick its set; `agent_loop` stops asking `research_depth`. No behaviour change.
2. *Waiting time (`wait_seconds`) in the queue, and the end of the hand-over.* The hand-over of heavy chat requests to the task queue (`handoff_*`, `handoff_slow_nodes`, which is set on the production hub) waits for a "fast node". The table of applications has the waiting time per row. **Needs a decision:** is "slow node" a property of a node (then the table or a measured speed says it) or of the row (then the order of the row already says it)? Recommended: drop `handoff_slow_nodes`, use the measured speed against the row's waiting time.
3. *`quality_models` and `second_look_model`.* The check model is the row `check`, the model of a summary the row `background`. The thorough stage of a chat picks its second model from `quality_models`; that moves to the row `check`. **Needs a decision** on what the effort level "thorough" does then (one model checks, or the row's list in order). Web: the settings page for the levels goes.
4. *The hub-wide default model* (`default_chat_model`, `resolver.default_model()`, 25 places) stays only as the last fallback of a row that names nothing.
5. *Split `api/chat.py`* (3300 lines) along its seams, after 2 and 3 because it touches the same places.

**Not decided here.** Whether a program may widen its ceiling per person (the profile of the person narrows it today, never widens). Whether Development and Administration tasks started by a project request should keep the full set of the person's machines: today they follow their program's ceiling, which for Administration is the servers.
