# D123 — The CI builds; the maintainer signs and rolls out

> **Status (2026-11-25):** Decided by the maintainer. Not built yet. Replaces [D13](D13.md).

**Decision.**

- **Hub image.** On every merge to `main` the CI builds the hub image and pushes it to the GitHub container registry, tagged `sha-<commit>` (and `test`). The actions of every workflow are pinned to a commit SHA, not to a tag. `scripts/dev/release.sh` can roll out such an image instead of building one locally (`--image ghcr.io/<owner>/sloppy-topcoat-hub:sha-<commit>`); its other steps stay as they are: backup tag, checks, smoke test, the way-back image on the server, `deploy/update-hub.sh` with dump, health check and automatic rollback, one question per step.
- **Node binaries.** The CI builds them as a **workflow artifact** with `SHA256SUMS`, not as a public pre-release. The maintainer checks the hashes and signs the release in the browser ([D80](D80.md)); the hub serves it through the update channel ([D50](D50.md)). The signing key never reaches the CI.
- **Local builds stay possible.** `release.sh` without `--image` builds locally as before, so a release never depends on GitHub being reachable.

**Why.** Builds in the CI are clean, tied to a commit and cost nothing for a public repository, and they keep load off the home machines. A rollout, however, belongs to the person who runs production, with the checks and the way back that `release.sh` already has. Unsigned binaries published on every merge looked like a supported channel and could not be installed as updates anyway; pinning actions by SHA keeps a changed third-party action out of an image the hub runs.
