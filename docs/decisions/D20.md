# D20 — Strict per-user isolation of everything personal

**Decision.** **Strict per-user isolation of everything personal.** Conversations, memory, private knowledge sources, uploads, API keys and agent tasks belong to one user; every query is scoped by `user_id` at the data-access layer (not only in the GUI), and retrieval/recall for a chat or agent runs only over the data of the user who started it. An agent acts **with the rights of its user**: which nodes, capabilities, models and knowledge sources it may use comes from that user's permissions (admin vs. user, per-node/per-capability grants), never from the agent. Shared data exists only as explicitly shared sources owned by an admin. Cross-user exchange between agents (ask/offer information) is **not** built now; if it comes later it must be opt-in per item, approved by the owning user, and audited.

**Why.** The service will be offered to family members: nobody may be able to ask the chat about what another person discussed, and a user's agent must not gain rights through another user's settings. Enforcing it in the data layer from the start is far cheaper than retrofitting it (same reasoning as D8).

**Amendment (2026-11-03): a conversation without an application.** A conversation made from the browser that names no application belongs to Chat (`api/chat.py`, `DEFAULT_APPLICATION`), so Chat's tool ceiling applies (`app_scope.py`). Before, such a conversation had no ceiling beyond the person's grants, while the interface showed it as a Chat; one with GitHub and machine-state tools was found that way. A program that calls the API with a key and names no application keeps the old behaviour: no ceiling beyond the person's grants. The web names the application on every start (`useChat`, the library). Existing rows with no application are not changed by the code: `UPDATE conversations SET application = 'chat' WHERE application IS NULL AND user_id = ...` is a hand step per person, to be looked at first.
