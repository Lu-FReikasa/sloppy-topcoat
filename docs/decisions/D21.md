# D21 — Chat

> **Status (2026-11-25):** Amended. Stop by disconnect is replaced by [D39](D39.md). The default-model chain is replaced by [D115](D115.md) and [D117](D117.md): there is no hub-wide default model setting. The system prompt is built by the core block ([D38](D38.md)) and the contracts ([D118](D118.md)). SSE, `ChatStore` scoping and Continue hold.

**Decision.** **Chat (E2-01).** The GUI chat talks to the models through the same gateway as external clients (`Gateway.route` / `forward`), so routing, fallback and cancellation behave identically. Conversations and messages live in the DB with `user_id` on both tables, reached only through `ChatStore(db, user_id)`, which filters **every** statement by that user (no helper takes a bare id); another user's id answers 404. The answer streams to the browser as SSE (`meta` with node/model/fallback/context info, `delta`, `done`/`error`); leaving the page or pressing Stop cancels the model request and stores what arrived as a `stopped` answer. **Context:** the hub has no tokenizer, so it budgets with a conservative estimate (3 characters per token, reserve = a quarter of the context, at least 256) against the context length the node reports for the loaded model (default from `TOPCOAT_CHAT_DEFAULT_CONTEXT_TOKENS`); the oldest turns are left out of the prompt (not summarised, nothing is deleted) and the GUI says so. The system prompt is a fixed language rule (answer in the language of the last message) followed by the user's own text. Default model: conversation choice, else the user's default, else the hub default (`hub_settings`, admin), else `TOPCOAT_DEFAULT_CHAT_MODEL`. **Follow-ups after the first hardware test:** the system prompt is built from the *real* capabilities (`chat.Capabilities`: memory, knowledge, web search, tools — all off until E2-02..E2-04 switch them on per user) and says what the assistant can and cannot do, forbidding claims beyond that; it also carries the Markdown rule (no ```` ```markdown ```` wrapper around ordinary text), the language rule and the user's form of address (`du`/`sie`, default `du`). A model answer that ends with `finish_reason: length` is stored as `truncated` (not `complete`); `POST /api/conversations/{id}/continue` asks the model to go on and appends the text to that same message. **Continue keeps the end of the cut-off text:** the continue prompt is the older turns, the question, the *tail* of the truncated answer as an assistant turn (marked `[…]` when its beginning had to go) and the instruction to go on exactly there without introduction; older turns are trimmed first, the tail gets 60 % of the free budget when it competes with the question, and if not even a minimum (about 48 tokens of tail and 16 of question) fits the hub answers 409 `context_too_small` instead of letting the model improvise. Contexts below 4096 tokens get a short system prompt (about a third of the size). `first_token_ms` and `duration_ms` are measured from the request (so they include a load on demand and prompt processing). The context a node loads a model with is configurable per node and model (PROTOCOL "Context length of loads"). Users other than the seeded admin sign in with API keys until OIDC (stage 5); keys never open the admin API.

**Why.** One path for every model request; isolation enforced where the data is read (D20); trimming instead of summarising avoids a second model call whose quality and cost are unknown — summarising can be added behind the same `build_prompt` later.
