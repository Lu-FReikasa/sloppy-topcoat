# D24 — Local use comes first

**Decision.** **Local use comes first ("ducken").** On every node, laptop or desktop, Windows or Linux, model processes yield in three steps, each configurable per node (`config.yield`): (1) always the lowest process priority (Windows `IDLE`/`BELOW_NORMAL`, Linux `nice 19` + `ionice` idle) for `llama-server` and `llama-bench`; (2) **freeze/thaw** — on user input within `idle_seconds`, foreign CPU load above `cpu_percent` for `sustain_seconds`, or battery power the processes are suspended (`NtSuspendProcess` / `SIGSTOP`) and continued at the same place on idle; requests in flight get the status `paused` (message `proxy_status`, forwarded to the chat as an SSE `status` event) instead of a timeout and the hub routes no new work to a paused node; (3) **unload/resume** — after `unload_after_pause_seconds` or when RAM/VRAM is needed (D16) the node unloads; the hub remembers the state: a multi-step deep task continues at its next step, a half-finished chat answer with the Continue logic (D21). New node state `paused` (precedence: `busy_gaming`, `degraded`, `yielded`, `paused`, `available`); events `paused` and `resumed`. Built as: `providers/activity` (input, foreign CPU load, battery), `internal/yield` (pure state machine with sustain/resume hysteresis), `agent/yield.go` (freeze, thaw, unload; `proxy_status` to the hub, SSE `status` to the chat), the runner's `Freezer`; an answer cut off by the unload ends with the error code `interrupted` and is stored as `truncated`. Detecting input from a Windows service (session 0): the virtual service account may not ask `WTSQuerySessionInformation` ("Zugriff verweigert", seen on the real laptop), and `GetLastInputInfo` only sees the caller's own session, so `topcoat-node input-helper` runs in the user's session (a scheduled task "at logon of any user", group principal *Users*, no stored password — S4U is not used) and answers the service over a local named pipe (`\\.\pipe\topcoat-node-input-<session>`, remote clients rejected, ACL: only the service SID, served from the console session or not trusted); the WTS query remains the fallback. The node keeps working on CPU-load and battery signals where input cannot be seen. The CPU-load signal combines the busy time with Windows' Processor Utility (a hybrid CPU never reaches 100 % busy time), the hypervisor's run time and the vmmem processes' time (WSL2 guests are invisible to the host's idle time).

**Why.** The laptop is a permanent part of the infrastructure but its owner must never think about it. Suspending instead of killing keeps a 30B prefill from starting over; the priority step alone is not enough because a busy CPU still stutters the UI. Everything hardware-specific sits behind interfaces with fakes (working rules).
