# D27 — Node resource guards and prompt order

**Decision.** **Node resource guards and prompt order.** (a) The benchmark logs a failing backend and goes on. (b) Models larger than a *discrete* GPU's memory are loaded with llama.cpp's own fit (`--fit on`; if the load still dies of an allocation failure the node retries with half of the layers, then on the CPU), backend and offload per model (`runner.model_backends`); processes of different backends run side by side. An *integrated* GPU gets no partial offload: its host and pinned buffers come out of the same shared budget as the layers, so a split always failed on the real laptop. The node plans the whole model on the iGPU when weights + KV cache + reserve fit the shared memory minus a safety margin (and what models on it already hold), otherwise it goes straight to the CPU, without a failed attempt in between. (c) Before a load the node checks model + KV cache + overhead against free RAM (an iGPU's shared memory is system memory) and refuses with `insufficient_memory` instead of swapping; the reserve defaults to the larger of 4 GB and 12 % of the RAM; RAM pressure handling defaults to on for nodes without a dedicated GPU. (d) The inventory reports free/total disk of the model drive; downloads that do not fit are refused. (e) Chat prompts are ordered for the prompt cache: fixed parts first (the system prompt is identical for every question and only says how to read the notes block), per-question content (notes, later retrieved passages) last and in front of the final user message, `cache_prompt: true`; stored turns carry no notes, so the previous exchange is read again with the new question, everything before it comes from the cache (measured against a real llama-server: prompt tokens processed per question grew from 1331 to 4449 over six questions before, and stayed at about 1300 after). (f) A model load is a job of the node, independent of the request that started it: requests for the same model join it, unloading cancels it, and its outcome is always an event (`model_loaded` / `model_load_failed`); the hub waits for `models.load` as long as the gateway does and stores a late `action_result` as an event. Cancelling really kills the half-started `llama-server` (event `model_load_cancelled`), and every attempt of a staged load re-checks the RAM guard and waits until the failed process has released its memory. (g) Every `llama-server` start gets its own random API key (key file, never on the command line) that only the node knows and adds to the requests it forwards, and CORS is limited to localhost. (h) The KV estimate follows sliding-window attention (Gemma 3/4: only the full-attention layers grow with the context, the others keep their window; shared-KV layers count none) — a 12B with a 16384 context was refused for "KV cache 24576 MB" and really used 7.5 GB of VRAM (E3-01e).

**Why.** Found on the real machines: one Vulkan failure aborted the whole benchmark, a 30B model on a 32 GB laptop left 0.4 GB free, and memory notes at the front of the system prompt forced a full prefill (37 s) on every question.
