# D29 — Tool nodes

**Decision.** **Tool nodes: the assistant looks at servers through read-only capabilities (E2-04).** A server pairs with `--role tools`: no runner, a config with `capability.invoke` and a fixed set of capabilities compiled into the node binary (system, disks, containers, container logs, compose projects and files, journal, systemd units). They are the D4 whitelist made concrete: no shell, no generic exec — Docker over `GET` of three endpoints (through a read-only socket proxy on the loopback or the socket, never a remote address), `journalctl`/`systemctl` by fixed argument lists, files only by name rules inside the compose project; every input is strict-schema, outputs are size-limited and **masked on the node** (secrets never leave the machine). The hub decides **who** (D20): the admin on the GUI, everybody else by grant per node and capability; an API key never inherits its admin's rights. The hub runs only capabilities that are `read_only` in the node's own inventory (D15: anything that changes state is a different path with the confirmation of that single action, stage 3) and writes **every** call — refused ones too — to an audit log. Chat tool use moved into the agent loop (stage 3): the model will call these same capabilities, with the rights of its user.

**Why.** The maintainer's first goal is an assistant that reads logs and Docker state on the servers, finds problems and — only after confirmation — fixes them. Reading must be safe by construction (nothing in the read path can write), so a wrong conclusion or an injected instruction in a log line costs at most a wasted read; the audit log makes every look traceable.
