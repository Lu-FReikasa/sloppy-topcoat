# D30 — The agent loop

> **Status (2026-11-25):** Amended. The limits are changed for Research by [D101](D101.md); role, tools and limits per application are [D118](D118.md); the forms of the answers are [D119](D119.md).

**Decision.** **The agent loop (E3-01a): a background task per user that looks, collects evidence and writes a diagnosis — it cannot change anything.** The loop asks the model (through the gateway, like every other model call) for one JSON action per turn; the tools are the read-only capabilities of D29 that the task's user may run (D20), called through the same hub service as the GUI and audited with the task id. Every result is stored as `[live]` **evidence** with its source; the diagnosis is a list of claims tagged `live` (must cite evidence that shows it — the hub downgrades a claim that does not), `doc` (E3-03) or `assumption` (says how to check). Tool output reaches the model as fenced data under a random nonce and never changes the task, the tools or the rights; the loop has no state-changing tool at all (proposals and their execution after a click are E3-01b, D15). Tasks, transcript and evidence carry `user_id` and are reached only through that user's store; progress events go to the owner's stream only. A task is cancelable and survives a hub restart (transcript rebuilt from the stored steps); limits per run end it with a diagnosis, never a hang. The hub starts **one agent generation per model** at a time, and a model's slots are configured small (`runner.n_parallel`, default 1: the configured context is the context of one request) so long generations do not eat each other's window; a "context full" answer is the retryable error `context_full`. Tool mode per model (E3-01c): native OpenAI tool calls (`--jinja`, one function per capability plus `finish`, `tool_choice: required`) or the JSON protocol, `auto` by default with a fallback — both store the same steps. **Hardware-test follow-up (E3-01e):** a reply cut off at the output limit is told apart from an invalid action (the limits are 1536/2048 tokens; a `finish` with a complete summary is rescued as a diagnosis without findings); the hub asks a node for 16384 tokens of context per slot when it loads a model for an agent and notes it when a model runs with less; `docker.ps` is compact by default.

**Why.** The maintainer wants the assistant to find problems on the servers, but a wrong conclusion or an injected instruction in a log must cost at most a wasted read. Forcing every claim to say what it stands on — and downgrading it when it stands on nothing — keeps "I saw it" and "I guess" apart in the GUI; the prompt-based JSON protocol works with whatever model the nodes serve and is easy to test with a scripted model.
