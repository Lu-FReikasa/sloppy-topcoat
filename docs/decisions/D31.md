# D31 — The chat uses the agent loop

> **Status (2026-11-25):** Replaced by [D69](D69.md) (Chat has no server tools), [D66](D66.md) (the level does not pick the model) and [D112](D112.md) (routing by contract through the secretary, not by keywords).

**Decision.** **The chat uses the agent loop (E3-01d): a question about the user's servers is answered after a visible, read-only check.** The hub decides per message — `auto` by a cheap heuristic (no extra model call), `on`, `off` — and runs the D30 loop as a task of origin `chat` with the user's own rights and tight limits; the chat stream shows the steps (collapsible), then streams the answer, which is written from the findings and evidence excerpts and keeps the `[live]`/`[doc]`/`[assumption]` tags with references. The answer model and the loop's model are the conversation's (same gateway, same fallback: if the fast machine is not available the GUI says which slower one does the work); a failed check is stated in the prompt so the model cannot pretend. **The model decides (E3-04):** a model that makes native calls is offered one function, `look_at_my_systems`, in every chat turn and starts the check itself (the keyword heuristic only remains for models that cannot, and for a node name, which starts the check at once); the system prompt lists every group of tools offered. Notes are recalled for a question about the person only ("mein" about a thing is not one) and only above a floor. **Quality levels (E3-04):** `fast` / `balanced` / `thorough` per conversation (default per user, model per level an admin setting): fast = fast model, two tool calls, no second look; thorough = more steps and the big model reads the answer against the evidence again (stored with the answer, the external model is offered when configured). **Scope (E3-04):** per conversation the user chooses which servers and tool groups the assistant may use (default: their last choice); it narrows the grants (D20), never widens them, and is applied to the model's description, the decision function and the check task alike. **The heuristic's trigger was narrow (E3-01e):** `auto` checks only for a tool node's name, the user's own systems with a state/fault question, or such a question about the machines right now; a keyword such as *docker* alone starts nothing, and when in doubt the answer comes first and the browser offers the check. On a slow stand-in machine the check is warned about before it starts and held to two tool calls; `[live]` is only for what a result in the check shows, never for general knowledge. Memory is neither recalled for nor extracted from server facts. A check that fails after it collected evidence is *incomplete*, not absent: the answer gets the evidence and must say so (E3-01e).

**Why.** The operator wants one place — the chat — not a chat and a tasks page; the check stays the audited D29/D30 path (nothing new can be reached), and the heuristic keeps ordinary chats exactly as fast as before.
