# D35 — Web access is a read-only capability of a tool node

**Decision.** **Web access is a read-only capability of a tool node, with its own door for what leaves the network (E3-04).** `web.search` asks the maintainer's SearXNG (URL from the node config only), `web.fetch` reads one public page; both are off by default, their output is untrusted data (fenced) and evidence tagged `web` with the source URL. The node refuses everything that is not a plain public address — on every lookup answer and again when the connection is made, for each redirect — and the hub refuses a query or URL that carries private data (the redaction layer's detection: secrets, addresses, e-mail, node/user/own-domain names) *before* the node is asked — in `ToolService.invoke`, so for every caller, and a refusal is an audit row without the value — and the node checks the same again (defense in depth, error code `private_data`); the model gets the refusal and can rephrase. A run asks the web little (3 searches, 2 pages, none after a usable page): a simple question took nine calls and 79 s. **A run fetches only URLs it was given** (security audit 2026-11-27): a hit of its own searches, a page or picture a page it read listed, or a URL in the person's own message; the node checks the same against its own hits unless the hub vouches for the person's URL (`url_origin`, PROTOCOL.md "Web capabilities").

**Why.** A search engine cannot use a stand-in, so what the redaction layer pseudonymises for Claude (D33) is *refused* here; fetching a URL a model chose is the one place a node calls an address it was told, so it is opt-in and SSRF-hardened at the connection, not only at the name. The origin rule closes the other way out: a model that read an injected page could otherwise put what it read into a URL of its own making, and the data check sees only addresses and secret shapes; a URL that came from a search or from the person carries nothing the run read.
