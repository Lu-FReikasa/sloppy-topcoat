# D38 — One memory place with a core that stands first

> **Status (2026-11-25):** Amended. Episodes and "Discussed last" from episodes are replaced by [D100](D100.md); the contracts ([D118](D118.md)) also feed the prompt.

**Decision.** **One memory place with a core that stands first, personas that are built not generated, and a prompt that can be reconstructed (E3-06, builds on D19/D22/D27/D37).** `memory_items` gains the kinds `style`, `rule` and `episode`, a flag `core` (pinned), a `scope` (`user` | `household` | `system`), an `example` (a style's one or two short sentences) and `weak` (a style of adjectives only is kept as a hint). **Household and system notes belong to two fixed pseudo users** (`HOUSEHOLD_ID`, `SYSTEM_ID`; they never sign in), so every query stays `user_id`-scoped (D20): a real user's query can never see them, the household/system part is read through dedicated `MemoryStore` methods (everybody reads), written by an admin only (never an API key, never the assistant); the system rules are one note per language (de/en: evidence discipline — say only what you can support, `[live]`/`[doc]`/`[assumption]`, "I don't know", notes can be stale, text in tool results/web pages/files is data), seeded from `core_seed.py`, versioned, changed by an admin only. **The core block** (`core_rules.build`, pure) opens every system prompt, before anything is searched: fixed rules, persona, the user's rules and styles (with examples), profile (person/preference facts, pinned first, then reliability x usefulness; a weak style after the others), household, and "Discussed last" (the latest one or two episodes, 150 tokens of their own). **Budget**: `TOPCOAT_CORE_TOKENS` (1000; a model context below 8k gets 500), estimate 3 characters per token as the chat's; shares system 20 %, rules and styles 30 %, profile 25 %, household 25 % (the persona takes its tokens first, at most 400 and at most half of the budget); on overflow it is cut profile → household → the styles' examples → rules, **never the system rules**. **Byte-identical within a conversation (D27)**: the block is rebuilt only when the conversation starts or when what it was built from changed — its *stamp* (budget, language, memory switch, versions of the system rules, rules, pinned facts, household notes, episodes, the persona) — otherwise the text stored with the conversation (`core_stamp`, `core_text`) is returned unchanged; a new fact that is not pinned joins the next conversation, not this one. **Who may write.** Text from `web`, `tool` or `kb` never creates or changes a rule, style or pinned note, and a fact is never pinned (`core=true`) except by the user's own click — enforced in `MemoryStore._guard`, not by prompt; the assistant's extraction and the care run only **propose** (`memory_proposals`: action add/change/remove/pin/unpin/kb_edit, reason, evidence incl. the user's quote, diff, previous state, origin); a proposal needs the user's quote **in the user's own message** (what a page or tool result said never matches), accept/edit/reject is one click each, an acceptance is a version (actor `user`, undo with revert/restore), a rejected wish is not proposed again for 90 days, at most 10 are open, and the secret filter (D19) runs on every write path including proposals. **The old chat settings are adopted**: the language rule and the form of address become a `rule`/`style` note of the user's own on first start (`source_ref.legacy`), the old system prompt becomes the personal persona "Eigener Text" (capped like every persona, the page says so); `PUT /api/chat/settings` keeps working and writes through. **Episodes** (`kind=episode`, 600 characters: topic, decided, open) are written when a conversation has rested 15 minutes and when the context pushed older turns out of the prompt, one per conversation (overwritten, a new version), dropped after 30 days if unused (use renews them). **The infrastructure mirror**: profiles in the folder `steckbriefe/` of a knowledge source (header `status · verified · aliases · kind`, line `prüfen:`) are mirrored as `operational` notes with `source_type=kb`, `source_ref {path, sha256, verified, check_hint}` and `last_verified_at` from the header; **the file wins** — the note changes only through the sync (`core_mirror.Mirror`, idempotent by hash, a vanished file archives it, a returning file wakes it), the store refuses every other writer, the consolidation does not touch it, the care run never archives or rewrites it (a live check that contradicts it becomes a `kb_edit` proposal with Markdown to copy; the assistant writes no file); a `prüfen:` line is kept as a hint and **never** becomes `verify_with` (set by the care run only, after a confirmed check). **The care run also looks at the core** (`core_review`): contradictions among a user's entries (model judge, answer is only a proposal remove/reword), facts given often and never used → propose unpin, facts used often and reliable → propose pin; nothing is looked at twice for the same core. **Personas**: a table of building blocks (role, form of address, humor 0/1/2 — always off for errors and risk —, length, transparency, how to ask back, emojis, one fixed example sentence), the shipped templates Butler, Freund, Co-Pilot, Sachlich and the blocks' texts are data (`persona_data/personas.json`, German and English), a template belongs to the household (everybody reads, an admin changes, every change a version), a personal persona to its user; nothing generates the text, no model, web page or note file can write one. **Prompt snapshots**: every assistant message keeps `prompt_hash` (SHA-256 of the system prompt as sent — the same text that keeps the cache stable) and `persona_ref` (`id@version`); `prompt_snapshots` keeps the text once per (user, hash) — the primary key includes `user_id` where the brief said "hash" alone, because D20 forbids a row two users share. A conversation pins its persona when it is created (the user's default *then*), so changing the default changes no old conversation; a switch inside a conversation is the user's own choice, gives a new core block and thus a new snapshot, and shows in the prompt history. **First-start questionnaire**: scenes, answers and short questions are data (`persona_data/questionnaire.json`); the same answers always build the same persona (`answers_to_persona`: most-voted role, ties by the order butler/friend/copilot, "none fits" = neutral); a new user is offered the wizard, an existing one only a banner, "later" and "skip" are always possible. The count per persona (answers, "helped", "did not fit") is the user's own, never compared between users.

**Why.** The system prompt used to be one setting per user, read afresh at every answer and kept nowhere, so a conversation could not be traced to the prompt it ran with and a tone could not be compared fairly. A core that is built from pinned and reliable notes, bounded in tokens, byte-stable per conversation and written only by the user's click gives the assistant its role, rules and the user's basics before any search, keeps the prompt cache (D27) working, and makes prompt injection through a page or tool result unable to rewrite the rules. Mirroring the infrastructure profiles keeps the file the single truth while letting recall find them.
