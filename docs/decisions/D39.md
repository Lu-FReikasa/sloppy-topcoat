# D39 — An answer belongs to the hub, not to the browser

**Decision.** **An answer belongs to the hub, not to the browser (E3-07 D1, replaces the stop-by-disconnect part of D21).** The answer — preparation (routing, recall, the choice of a server check), the agent check, the model's stream, the memory extraction afterwards — is produced by **one task of the hub per answer** (`chat_runs.AnswerRuns`, started with `gateway.spawn`, so the shutdown drains it). The task writes into a message that exists from the start (status `running`; the text so far is saved every second; the result, the tokens and the prompt snapshot at the end) and publishes its events, numbered, to whoever listens. The SSE response of `POST …/messages`, `…/regenerate` and `…/continue` is only the first **subscriber**: closing it (another tab, a reload, a lost connection, a navigation) cancels nothing; a subscriber attaches again with the message id and the number of events it already has (`GET /api/chat/messages/{id}/stream?offset=n`, any number at once, each gets the same events) and, when the run is over and gone from memory (kept five minutes) or the hub restarted, gets one `snapshot` event with the stored message. **Stop is its own call** (`POST /api/chat/messages/{id}/stop`, or `POST /api/conversations/{id}/stop` while the model still reads the prompt and no event has named the message yet): it cancels the task, the partial text is stored as `stopped` (nothing said = the empty bubble is removed), the subscribers get a `stopped` event. A hub that goes down ends its runs first (`AnswerRuns.shutdown` before the engine is disposed): the text so far is stored as `interrupted`; one that was killed leaves `running` messages that the next start marks `interrupted` (`sweep_interrupted`); an interrupted answer can be continued like a truncated one. The conversation list carries `running` (the "runs in the background" chip). Failures before the model has started to answer are still HTTP errors with their codes (the request waits for the first outcome, shielded from its own cancellation); after that they are `error` events.

**Why.** The old design produced the answer inside the SSE request: a tab switch cancelled the model request and stored only the part that had arrived, so users sent the same question again and ended up with two. Making the generation a hub task with the stream as a reader fixes that class of problems for good (reload, second device, flaky mobile connection) and makes "stop" mean what it says. Writing the text so far into the database every second is what lets a restart end in "interrupted" instead of a lost answer.
