# D43 — The agent proposes, the person confirms one click at a time

**Decision.** **The agent proposes, the person confirms one click at a time (E3-01b, makes D15 concrete).** After a diagnosis the model may attach proposals to its `finish`; the hub stores them (`agent_proposals`, per user, immutable under a SHA-256 over everything shown and everything sent, with an expiry) only after checking mechanically that the action is one this user may confirm, fits its schema, cites live evidence and names only what a *listing or status* tool showed (so text in a log cannot put a target into a proposal). Execution is a different door: `POST …/execute` is refused for every API key, claims the row atomically (two clicks run it once), re-checks owner, state, expiry and hash, and sends **one** `capability.execute` to the node, which checks again (action allowed, capability switched on, not read-only, a confirmed proposal's id and hash present, target on its restart list). The write capabilities (`docker.restart`, `service.restart`) exist only where the node's config lists what may be restarted (default deny) and Docker is reached through a **second** proxy that allows only `POST /containers/{id}/restart` (the node binary's own `docker-restart-proxy`, a whitelist tested in CI; the generic socket-proxy image could not be narrowed that far: its restart switch also lets stop and kill through); the read proxy of D29 is unchanged. Everything is audited (`tool_calls.via = proposal`). The whole feature is off until an admin sets `TOPCOAT_PROPOSALS_ENABLED`; there is no blanket approval and the agent cannot confirm.

**Why.** The step from "finds the problem" to "fixes it" is where the risk is; one proposal, one click, one run keeps the person in charge and the audit complete. A mechanical check of the target, not a prompt, is what stops prompt injection from choosing it.
