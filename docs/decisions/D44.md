# D44 — The coordinator

> **Status (2026-11-25):** Note. This coordinator is the read-only check of several machines (Administration). The planned decomposition of large tasks ([D109](D109.md)) is a different thing.

**Decision.** **The coordinator: one question, one read-only check per machine, one merged report (E3-08).** A task of kind `coordinator` has no tool at all and starts no change. It asks the model once to split the question across the machines the user may look at (validated against the real machines; anything unusable falls back to one check per machine; a single machine needs no plan), starts every check as an ordinary agent task of the same user (`origin child`, `parent_id`, scope = that one machine, no internet, tighter limits), at most `coordinator_parallel` (2) at a time because a node has one model slot, waits, and merges: the children's evidence is copied into the coordinator's own so every finding keeps pointing at what it rests on, each finding carries its machine, and one model call writes the combined summary (a plain join when it fails). Depth is 1 (only this code starts children, a child is a plain task), the rights of a child are the user's rights narrowed by its scope and never wider (D36), children get no proposals (D43) and the coordinator none either, a run is bounded by `coordinator_max_children` and `coordinator_time_budget_seconds`, canceling the coordinator cancels every check, every start and result is a normal audited task (`user_id` everywhere), and a restart resumes from the stored plan. No Claude integration: the coordinator is an agent in the hub (maintainer's decision).

**Why.** Several machines are asked in one go without a new kind of power: the coordinator only reads, and any change it leads to is a D43 proposal with its own click. Low parallelism because more concurrent checks only queue for the model.
