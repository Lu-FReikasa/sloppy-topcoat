# D46 — Stacks and the inventory's buttons

**Decision.** **Stacks and the inventory's buttons: more container actions without a wider door (E3-11, builds on D29/D43/D45).** (a) *Read:* `compose.logs` reads the logs of every container of one compose project, merged by time with the service in front of each line (one call instead of one per container; at most 20 containers, a container that cannot be read is reported, not fatal; masked like every log). (b) *Change:* `compose.restart` restarts the **running** containers of one project one after the other, dependencies first (`depends_on` label), and leaves stopped ones stopped. It uses **no new Docker endpoint** — a series of the single restart call D43's write proxy already allows — and refuses the whole stack, before touching anything, unless **every** running container is on the node's `restart_containers` list; it stops at the first failure and says what was and was not restarted. (c) *Buttons:* the inventory page shows "Logs" and "Restart …" next to containers, stacks and units where this user may. A restart button does **not** run anything: it asks the hub for a *manual proposal* (`origin manual`, no task), which is stored, hashed and expiring exactly like the agent's (D43), carries texts from the hub's own templates in the user's language (no log text can be in them) and runs only on a second, separate click on the same card through the same execute door (signed-in user only, API keys refused, audited with `via proposal`). The agent gets `compose.logs` as an ordinary read-only tool and may propose `compose.restart` like `docker.restart` (the stack name must have been shown by `compose.projects`).

**Why.** The person should not need the assistant to restart a stack, but the confirmation must be the same: the exact effect on a card, one click, audited. Reusing the restart call keeps the most dangerous door (the Docker socket with write) as narrow as it was.
