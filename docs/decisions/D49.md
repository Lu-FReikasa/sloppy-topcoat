# D49 — GitHub as a read-only tool of the assistant

**Decision.** **GitHub as a read-only tool of the assistant (admin only).** One virtual tool of the hub, `github.read`, in the tool group `github`: the pull requests (list, one, files, reviews and comments, checks), the issues, a file or directory, commits, branches and a code search of **one** repository named in `TOPCOAT_GITHUB_REPO`. The model passes no repository, only what to look at. The client can send nothing but `GET`, every path comes from a fixed template for that repository with validated parts (a test records every request), and the token (`TOPCOAT_GITHUB_TOKEN`, a fine-grained personal access token with read rights only, never logged or part of an answer) lives in the hub's environment. The tool is offered to an admin only and only when token and repository are set. Text written by others (descriptions, comments, file contents) is returned with a note that it is data, never instructions, and secret-looking text is blackened. Writing (comment, merge, close) is a separate later step with its own token, the proposal flow and a click (D15); nothing here prepares it.

**Why.** The operator wants the assistant to see the code and the PR chain it helps to build; a read-only door with one repository and one token keeps a wrong answer or a prompt injection in a PR text from changing anything.
