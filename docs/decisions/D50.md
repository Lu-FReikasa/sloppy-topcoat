# D50 — A signed update channel for the nodes

> **Status (2026-11-25):** Open question. [D80](D80.md) moves signing into the admin's browser; this text signs with `topcoat-sign` on the maintainer's PC. Align both with the way releases are signed today.

**Decision.** **A signed update channel for the nodes (E2-06).** Builds are signed on the maintainer's PC with an Ed25519 key that never leaves it (`topcoat-sign`; GitHub Actions is not used). The hub only stores and serves them (`TOPCOAT_UPDATE_DIR`, newest two per channel and platform); it never signs and never pushes. A node follows one channel (`config.update.channel`, default `stable`) and updates only when the admin clicks *Update* (action `node.update`, D15, audited like every action; the assistant has no path to it). The node (unprivileged) downloads over its existing outbound connection (signed-nonce request, no new port), verifies signature, channel, platform, version, size and SHA-256 and *stages* the bundle in its data directory. A second small service, the **updater** (`topcoat-node updater`, same file; Linux root, Windows LocalSystem) is the only one that may write the program file: it re-verifies the bytes it read itself against up to two public keys built into the program (`-ldflags`), refuses anything that is not strictly newer or not for this platform, stops the node, keeps the old file as `.prev`, starts the new node and waits for its confirmation (written after the hub accepted it); without it within 120 s the old program is restored. A crash in between is recovered from a marker on the next start. The updater's own files (marker, heartbeat, result) live in a directory that only the updater's account may write (Linux `/var/lib/topcoat-node-updater`, Windows `%ProgramData%\\topcoat-node-updater`), never in the node-owned data directory, so the node account cannot steer root writes with links; the updater also refuses linked directories. A build without keys is not update-capable and refuses `node.update`.

**Why.** Every node update was a manual elevated command on three different machines. The design keeps the cost of a wrong or taken-over hub or node at "a validly signed, newer build": the service account cannot make the root updater install anything else, the hub holds no key, and a failed start rolls back by itself. A reserve key allows a key change without visiting every machine.
