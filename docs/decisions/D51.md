# D51 — Models move directly from node to node

**Decision.** **Models move directly from node to node (E2-07).** The hub coordinates, the data never touches it. The baseline says nodes open no listening port; this decision allows one narrow exception, and nothing else: **no standing listener** (the source opens a TCP socket only when the hub instructs it to send one specific model, and closes it after one successful transfer, on error, or after a timeout, default 10 min; without an instruction there is no open port); **one connection, one peer, one file** (the socket serves a single peer: the source checks the peer address against the candidates the hub gave for the target, and every request must carry a one-time token of 32 random bytes, issued by the hub per transfer, sent to both nodes over their authenticated sessions, held in the hub's memory only and never stored or logged); **TLS with pinning, no CA** (the source makes an ephemeral self-signed certificate per transfer; the hub passes its SHA-256 fingerprint to the target over the authenticated session and the target pins it; plain TCP is not offered); **only a model file from `models/`** (the source resolves the name inside its own `models/` directory and the configured read-only `model_dirs`, never a path from the wire; nothing else is reachable through this socket); **hub-assigned whitelist** (two actions, `models.send` and `models.receive`, run only on nodes whose `allowed_actions` contain them, D15; the maintainer starts each transfer in the GUI). Not a remote shell, not a file server, no second protocol surface: one verb, one file. Mechanics: `POST /api/model-transfers` creates a row (`model_transfers`, scoped by `user_id`, D20) and dispatches `models.send`; the source reports `transfer_ready` (port, addresses, SHA-256, certificate fingerprint); the hub dispatches `models.receive` to the target with `address:port` endpoints (addresses the node reported first, then the address the hub sees it connect from); the target tries them in order, pins the fingerprint, resumes from its `.part` file and verifies the hash. With `move` the hub sends `models.delete {confirm: true}` to the source only after the target reported `done`. One transfer per node at a time; one that makes no progress for 15 minutes fails with `timeout`; rows left running by a hub restart fail as `interrupted`. No route (different networks, firewall) is a clear `no_route` error; there is no hub relay and no NAT hole punching.

**Why.** Models are large and the maintainer owns several machines on a routed LAN/VPN; sending them through the hub doubles the traffic on its link and copying by hand is slow and error-prone. A direct connection is the simplest thing that works on Windows and Linux without a new dependency (Go standard library: TCP, TLS 1.3, HTTP/1.1 with `Range`). The exception is kept as small as the task allows: the port exists only during an instructed transfer, accepts one authenticated peer and serves one file, so a compromised hub or node still cannot read other files or get a shell.
