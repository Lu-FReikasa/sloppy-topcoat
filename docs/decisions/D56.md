# D56 — One record of what the hub does for an answer

**Decision.** **One record of what the hub does for an answer (E7-01).** The chat used to show a transient progress line and, at the end, a report card; what the model thought, which call failed and why, and what the hub decided in between was gone when anybody looked. ``activity.py`` keeps an ordered list of *items* per answer: a thought (``reasoning_content`` of the model or a ``<think>`` block, which used to be dropped), the text a model said before it called a function (it used to be thrown away with ``discard``), the call that runs now and how it ended (``ok`` or ``failed``, with the reason code), a plan line, the second look at an answer, a note the person sent. An item is plain data without a sentence: the browser words it in the user's language. Every change is a chunk of the answer's SSE stream (``event: activity``), so the chain grows while the answer is made and a tab that attaches later replays it (D39); the finished list is stored with the answer (``messages.activity``). A failed call is shown as failed at once, not in the report at the end. The person can **pause** a running check and send it a **note** that it reads before its next turn (``steering.py``): a note is text from the person who asked, put where a tool result would be; it widens neither the check's rights nor its tools (D30), a pause does not use up its time budget and one nobody ends is ended after 15 minutes.

**Why.** A "thinking …" that hides everything cannot be corrected: nobody can step in when a model drifts or most of its calls fail. The record is the single source for the live view, the stored view and (D59) the view of a flow. Steering is read-only on purpose: the person's words are the only thing that can change the course of a check.
