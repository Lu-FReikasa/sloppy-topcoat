# D59 — Flows

**Decision.** **Flows: the steps between a question and its answer as a graph (E7-05).** A flow (``flows/``) is data: nodes (a model call, the read-only check of the servers, a planner, a step runner in which a second model reads each result, a router, a report) joined by edges that leave a node by a port (``ok`` / ``fail``, ``yes`` / ``no``). The text parameters of a node, its prompts included, hold references such as ``{{input.question}}`` or ``{{plan.out.steps}}`` that are looked up in the data of the run; nothing is evaluated. The hub runs the graph: nodes that are ready together work side by side (``flow_max_parallel``), a branch that was not chosen disappears as a whole, a failure leaves by the node's ``fail`` port or stops the run naming the node and the reason. Every save is a **version** (``flow_versions``, never edited), a run keeps the version it started with, a graph that is not saved can be run to try a change, and the parameters of a node that has not started can be changed for the run that goes on. The events (``flow_node``, ``activity``, ``flow_done``) are numbered like those of an answer, so a browser may leave and come back; a finished run is stored. A run has the rights of the admin who starts it; its check is a task of that person (origin ``flow``) and can do what a check can do — look (D29, D30): a flow arranges the read-only pieces differently, it adds no power. Three flows come with the hub and are copied to be changed. An admin can choose a flow per conversation (``conversations.flow_id``): the run then writes into the activity log of the chat turn, so the chain in the chat is the chain of the run, and the report the flow ends in is the answer.

**Why.** The way the hub turns a question into an answer was fixed in code, so tuning it meant a new image. As data it can be drawn, tried while it is drawn, watched while it runs and put back to an earlier state. A graph with explicit nodes shows which task is done where and which result goes to whom for checking.
