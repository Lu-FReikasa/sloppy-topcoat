# D76 — Local repositories in the dev workshop

**Decision.** **Local repositories in the dev workshop; external ones are read only.** A repository is `external` (it lives on GitHub; the assistant reads it with `github.read`) or `local` (its origin is a bare repository in the workshop of one dev node, `dev_repos.node_id`; the assistant edits and tests it on branches `topcoat/*` and keeps work with `repo.commit`). A local repository is created there or cloned from an external one, which stays its upstream (`dev_repos.upstream_id`). The person's own steps — create, clone, branch, take a branch into the default branch, publish, pull, remove — are node capabilities marked `manage`, run only by the whitelisted action `workshop.manage` from the hub's page (`tools.manage`, admin on the GUI, audited); `capability.invoke`/`execute` refuse them, so no assistant reaches them. A remote (clone, publish, pull) is an https URL from the allow-list with the token in one git call's environment; publishing and pulling are never forced. Old external rows in mode `test-branch` keep working; new external repositories are read only.

**Why.** The maintainer wants a dev environment that does not depend on an external service: the code lives and is tested at home, GitHub is an option to publish to. Separate kinds keep plain what the assistant may change; the default branch is the person's.
