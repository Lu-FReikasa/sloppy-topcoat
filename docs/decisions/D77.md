# D77 — One running summary per chat

**Decision.** **One running summary per chat; a section never waits for a summary.** Supersedes the *summary of the section that ends, waited for* of D54 (and the per-segment summary of D53). The digest of a chat (`chat_digests`, E5-01) is brought up to date after every answer by the model and node of that answer, from what it already noted plus the new messages: each answer is treated as the last one, and the digest is a growing history of the chat's main points. A new section, and the prompt after a rest, start from that digest plus the messages it does not cover yet, verbatim; without a digest from the verbatim end of the old chat. `SegmentService` writes nothing and calls no model, `POST /conversations/{id}/section` never answers `summary_pending`, and a message is never refused because a summary is missing. Summaries written for segments before this stay readable (hand-over and recall); no new ones are written. The earlier chats of a chain take part in the recall with their digests. What the background still does for a chat is shown on the page (`GET /conversations/{id}/background`: `running`, `waiting`, `idle`); the second look and the review stay on the node order of the admin and may lag behind.

**Why.** A chat that could not be answered left messages without an answer, each rest made another section that needed a summary from the hub's default node, and one slow node stopped the chat on another node (found live on 2026-10-23). A background job must never hold the foreground back; the duplicate section summaries added a second place where this could happen without adding information the digest does not have.
