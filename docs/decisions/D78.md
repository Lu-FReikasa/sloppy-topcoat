# D78 — Model roles

> **Status (2026-11-25):** Replaced by [D85](D85.md), [D115](D115.md) and [D117](D117.md).

**Decision.** **Model roles: one place decides which node and model do which work (consolidation steps 3 and 4).** Four roles -- `answer`, `agent`, `background`, `check` (the second look) -- each an ordered list of `(node, model)` in the node policy; a model may be `default` (the default model of that node, `NodePolicy.defaults`, set in one place on the scheduling page, so one change moves every application that did not pick another), `auto`, which takes on that node the largest model that is still fast enough for the role by the speeds the hub measured (30, 15, 5 and 5 tokens per second), or a name. An application may have lists of its own (`app_roles`); the person's pick in a conversation wins. `model_resolver.py` is the only code that answers "which model?" and returns the reason with the choice; the callers (chat, agent, care, digest, second look, hand-over, incognito, flows) no longer read settings. Removed: the node list per task, `chat_node_chain`, `gateway_node_order`, `gateway_background_nodes`, `gateway_background_model`, `memory_model`, `review_model`. Their values -- stored or in the environment -- are turned into roles once at start and the stored policy is rewritten (`node_policy.apply_environment`); the way back is the dump the update script takes. The applications are one list, `proto/ui/applications.json`.

**Why.** The answer to "which model answers?" was spread over twelve settings and seven copies of "the hub's default or the environment's", and the configured chat model on the GPU node ran at 12 tokens a second while a model almost as good ran at 200, measured by the hub itself. One resolver with a reason makes the choice testable and shows it in the GUI.
