# D79 — The context of a load is the smallest the work needs; growth is a node's cap

**Decision.** `models.load` takes `min_context_length`: the context per slot that the work needs (the hub asks 16384 for an agent run, 24576 for a research run). The node loads with exactly that, or with `runner.default_context_length` / `runner.model_context_lengths` if those are larger. The node grows the context beyond it only if its config names a cap (`runner.max_context_length`), and then only as far as the free memory minus the reserve allows (`memfit.AutoContext`, the same estimate as the memory guard). On a discrete GPU the part of the model the device does not take runs from RAM, so the context may still grow into free RAM when a cap is set. A larger need comes from the hub as a larger floor, which the node reloads for.

**Why.** A smaller context is faster, and most work needs no more than its floor. Growth to the largest context that fits made every load as large as the memory allowed, which slowed chats and agents without a need. The hub knows the need and asks for it; the node knows the memory and grows only when it is told it may. A fixed context per model in the node's config is still wrong when the need changes, so the floor comes from the work, not from the model.

**Changed 2026-11-09.** Before, the node grew the context on its own up to 32768 or the trained length, and on a discrete GPU only while the whole model fit the card. That left the agent at 16384 on a card that could never hold the model, and made every load large. Now: no cap, no growth; a cap opts in to growth into free RAM.
