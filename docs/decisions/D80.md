# D80 — A node is a machine

**Decision.** **A node is a machine; what runs on it are services, builds are made inside Topcoat and signed in the browser (brief NS-01-node-services-and-releases).** One machine has one node: one identity, one session to the hub, one entry in Administration. Compute (models), tools (read-only capabilities), development (the workshop) and, new, build (images and releases) are *services* of that node, each its own process under its own OS user, talking to the node over a local Unix socket the node reads the caller's uid from (`SO_PEERCRED`); the node itself opens no port and runs unprivileged. The hub's whitelist of actions is per service. The *build* service builds from a pinned commit in a fresh clone and **never signs**; its artifacts travel to the hub over its existing outbound session. The signature is made in the admin's browser (the key file is read locally, Web Crypto signs the manifest, only the signature leaves the PC) and the hub publishes through the existing update channel only after verifying it against the configured public keys. Releases belong to Administration, not Development, and rolling out a hub image is a separate named action with its own click that wraps `deploy/update-hub.sh`. No agent, API key or schedule starts a build, a signature or a roll-out. Supersedes the statement that a node has one role set where it appears (D50 and the role text of docs/PROTOCOL.md): one node now has several services, and each service its own.

**Why.** The maintainer thinks in machines, and the overview listed one machine several times because privilege separation was done with several identities. Separation stays, but inside one node. A machine that builds code from a repository the development agent can write to must not hold the signing key, and uploading a key to a server cannot be made safe, while signing does not need it there.
