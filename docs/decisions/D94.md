# D94 — A node's queue is as large as the node says, and the node is chosen before the prompt, without holding a place

**Decision.** **The queue of a node (`job_queue.py`, SCH-03 steps 1 and 2) is as large as the sum of `n_parallel` of the models the node has loaded (absent counts 1); the flat limit `gateway_max_streams_per_node` is gone. The choosing rule is a pure function (`choose_next`): best place first (chat, after an answer, other), the oldest within a place, idle work only alone and only while no chat or answer work runs, only the head of the queue is looked at, running work is never cancelled. Waiting can raise a job one place per period (`gateway_queue_aging_seconds`, off until it is measured). A chat answer asks the gateway to choose the node and have the model loaded before its prompt is built (`Gateway.reserve`), so the prompt is sized for the node that really runs it; the reservation holds no place in the queue.** Built on 2026-10-31.

**Why.** The old limit of 8 streams let several requests reach `llama-server` at once, which then queued them itself, in arrival order and without a priority. A queue of the size the node reports puts the order in the hub, where the live view and the record can see it. The first version of the reservation held a place until the answer started; that was dropped before it ran: between choosing the node and asking for the answer the same turn makes other model calls (the memory search with an embedding model, which on a one-machine setup lives on the same node), and a held place would have made them wait for the answer they are part of, until their timeout. Not built: a `gateway.job(...)` context manager and one job per model call of an agent run (the brief SCH-03); they would need the held place and a way around that deadlock.
