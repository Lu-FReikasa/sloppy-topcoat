# D98 — Development may go live through an overlay; a release is an image

**Decision.** **`scripts/dev/deploy-overlay.sh` copies the hub's Python code, its migrations, `proto/` and, with `--web`, a built GUI to the hub host and starts the hub with those directories mounted over the image's copy (about ten seconds). It refuses uncommitted changes, writes a dump before the first start with different migrations and switches back to the image code by itself when the hub does not answer. The overlay is not a release: it is not reproducible from an image tag, it cannot change Python dependencies or the Dockerfile, and every session that used it ends with a clean image (`scripts/build-hub-image.sh`, `deploy/update-hub.sh`), whose update uses the base compose file only and so removes the overlay.** Not built, on purpose: replacing single functions in the running process, and any way to upload code through the hub's API (the nodes' rule, no generic remote code path, holds for the hub as well).

**Why.** An image build, transport and recreate took the better part of an hour per round, which was the bottleneck of every live test. The overlay makes a round ten seconds and the clean image after a warmed Docker cache a few seconds. Reloading functions in a running process was rejected because `from x import f` keeps old references, modules hold singletons and tasks are in flight; a restart costs seconds. A code upload through the API would be exactly the generic code path the security baseline excludes; the overlay is files on the host, reachable only by whoever can already log in there. Tried on 2026-10-31: three pushes, the rollback path itself was not triggered.
