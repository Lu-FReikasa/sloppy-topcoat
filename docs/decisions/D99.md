# D99 — A change to a registered repository is confirmed one by one

> **Status (2026-11-25):** Amended by [D103](D103.md) (a fix as one set) and [D108](D108.md) (probe mandate).

**Decision.** **The assistant never changes a file in a registered repository with a call of its own. It proposes each change (`repo.write`, `repo.edit`, `repo.apply_patch`) in the proposals of its finish, and the user confirms each proposal with one click, as for every other state-changing action (D15, D43).** Reading, searching, starting a work branch (`repo.start`), running the tests and the one-click push (D52) stay as they are.

**Why.** D52 let the assistant change files in the scratch copy of a workshop node without asking, and kept the only click for leaving the workshop (the push). The maintainer asked for a confirmation per change, because a wrong or injected change should be seen before it lands in the copy the next tasks use. The proposal path already exists for node actions (D43); a scratch change becomes a proposal like the others.

**How it is built.**
- `ToolService.writable` (tools.py) includes the scratch edits of the workshop (`agent_workshop.CHANGES`), so they are proposable. Only an admin or a grant that names the capability can confirm them (D15).
- `AgentService` (agent_service.py) leaves the edits out of the list of direct calls, so the agent cannot run them itself.
- `ProposalService.execute` runs the confirmed change through `execute_confirmed`, the same path as any proposal.
- The workshop hint (agent_prompts.py) tells the agent to propose each change, one per file, after reading the file in the same run.
- A question that names a repository now selects the `workshop` group (tool_groups.py). Before, "repo" selected only GitHub, so the dev node's tools were never offered.

**Consequences.**
- A task cannot write, test and fix in one run. The change is proposed at the finish, applied on the click, and the tests run afterwards (the test run is still a direct call).
- The proposal card shows the input of the change. A full diff of a file is not shown yet; that is a follow-up (the card should show the diff before the click).
- D52 is changed for file edits only: the push and the test runs keep their rules.
- Admin-only confirmations stay as they were: a non-admin needs a grant that names `repo.write`.

**Not decided here.** Whether a change should also be confirmable as a batch, and how the diff is shown. Both are follow-ups.

**Amendment (2026-11-03): grounding and diff.** The first version of D99 made the edits proposals but left the proposal
check as it was for actions on machines (every string of the input must appear in a container or unit listing), which
would have dropped every file change. A file change is now grounded in a read of that file in the same run (a new
file: any look at the repository; a patch: any look at its repository), and the proposal carries the change as a diff
(`preview`, part of the hash) that the card shows before the click (`proposals.py`, `workshop_ground`,
`workshop_preview`). The node still checks when the change runs that the old text occurs exactly once.
